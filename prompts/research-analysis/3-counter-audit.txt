OPPOSITIONAL CITATION & NEGLECTED EVIDENCE COUNTER-AUDIT PROMPT (v3)

-----------------------------------------------------------------
INSTRUMENT PREFLIGHT — MANDATORY FOR FORMAL / LOGGED RUNS   [TOOL-004]
-----------------------------------------------------------------

This prompt is part of the audit instrument. Establish the exact instrument version BEFORE
substantive retrieval, extraction, analysis, or verdict work begins.

A successful fetch indicator, correct repository path, branch label, plausible line count,
matching rendered metadata, or internally self-consistent page does NOT by itself establish
that the intended/current artifact was retrieved. A mutable remote reference can return a
historical representation that is internally self-consistent in every visible field.

PROMPT IDENTITY MARKERS

  - OPPOSITIONAL CITATION & NEGLECTED EVIDENCE COUNTER-AUDIT PROMPT (v3)

These markers confirm the prompt family / expected structural features. They do NOT by
themselves establish version currency: an older version may share the same title or markers.

1. RECORD THE INSTRUMENT ACTUALLY IN CONTEXT.

   Record, where available:

   - canonical prompt path or supplied filename;
   - retrieval form: PASTED / ATTACHED / IMMUTABLE REMOTE / MUTABLE REMOTE;
   - requested branch or ref;
   - intended immutable commit/ref, if the run claims a repository version;
   - resolved commit SHA;
   - resolved blob/content hash, or a locally computed cryptographic content hash;
   - exact line count and byte count;
   - prompt identity markers present / absent.

   If a pasted or attached artifact is itself the declared instrument under test, its computed
   content hash may serve as its identity. Do not claim it is the current canonical repository
   version unless that relationship is independently established.

2. MUTABLE-REFERENCE / CURRENCY RULE.

   A path such as /blob/main/, /blob/master/, latest, or another moving branch/ref is a LOCATOR,
   not an immutable version identity.

   Ordinary exploratory work may use a mutable locator with the limitation preserved.

   A FORMAL / LOGGED / BENCHMARK / REGRESSION / FIXTURE run that claims the current repository
   instrument must establish an immutable intended identity independently of the mutable-content
   fetch. Acceptable examples include:

   - an operator-supplied immutable commit permalink;
   - a branch-head / repository-history lookup independent of the content retrieval, followed by
     retrieval of the file at that immutable commit;
   - a second retrieval path that does not reuse the same cache/index, confirmed against an
     immutable commit/blob identity.

   A commit/hash/line-count reported only by the SAME potentially stale rendered representation
   is NOT independent currency evidence.

   If no independent immutable anchor can be established and no explicit collision is observed,
   classify:

     INSTRUMENT VERSION UNVERIFIED

   Such a run may be exploratory but may not count as formal regression or benchmark evidence
   for a claimed canonical version.

3. VERSION-COLLISION ATTRIBUTION GATE.

   If the retrieved representation disagrees with an expected hash, immutable ref, size, line
   count, marker set, or independently established version, classify only:

     VERSION COLLISION — UNRESOLVED

   A failed identity check proves a VERSION MISMATCH. It does NOT establish where the stale
   representation lives. Do NOT conclude from the conflicting retrieval alone:

     REPOSITORY STALE
     RETRIEVAL STALE
     LOCAL COPY STALE
     OPERATOR COPY STALE

   Attribution requires a SECOND, INDEPENDENT discriminator, such as:

   - an immutable commit/blob lookup;
   - repository/file history;
   - a second retrieval path that does not reuse the same cache/index;
   - direct operator confirmation supported by an immutable identity;
   - a locally supplied file whose hash can be compared independently.

   Internal self-consistency is NOT an independent discriminator. A stale representation may
   have a mutually consistent path, branch label, line count, byte size, line gutter, content,
   and rendered repository metadata because all were produced from the same stale snapshot.

4. DISPOSITION.

   FORMAL / LOGGED / BENCHMARK / REGRESSION / FIXTURE RUN:
     - IDENTITY CONFIRMED against the intended immutable instrument -> continue.
     - VERSION COLLISION — UNRESOLVED -> STOP before substantive execution.
     - INSTRUMENT VERSION UNVERIFIED -> exploratory execution may occur, but the run may not be
       logged as evidence for the claimed canonical instrument.

   ORDINARY EXPLORATORY RUN:
     - May continue with INSTRUMENT VERSION UNVERIFIED when no collision is observed.
     - If a collision is observed, do not make claims about repository/instrument state until
       the collision is independently resolved.

5. REQUIRED RUN-HEADER LINE.

   Emit this before the substantive body:

   INSTRUMENT PREFLIGHT: [path/file] @ commit [SHA/UNAVAILABLE] | blob/hash
   [HASH/UNAVAILABLE] | [N] lines | [N] bytes | markers [PRESENT/ABSENT] |
   [IDENTITY CONFIRMED / INSTRUMENT VERSION UNVERIFIED /
   VERSION COLLISION — UNRESOLVED]

   If VERSION COLLISION — UNRESOLVED is returned, also state the conflicting identities and the
   independent discriminator required to resolve them. Do not silently choose one.

GOVERNING RULE:

  A failed identity check proves a version mismatch, not where the mismatch lives.

Purpose: You are now running an adversarial counter-audit against the outputs of one or more
prosecuting stages (construct-validity, internal-validity, citation-network) that examined the
same source and claim map. The primary object of this counter-audit is the PROSECUTION ITSELF
- whether it attacked the right claim, engaged the source's own defenses, and survived contact
with the strongest opposing evidence. If a synthesized thesis paragraph or short paper draft
already exists (see Input 5), this stage ALSO checks that draft's fidelity to the vetted
prosecutor findings, as a secondary, optional pass - see the FIDELITY CHECK block after
Section J.

The goal is not to find more evidence for the audit. The goal is to find the strongest
evidence that opposes, complicates, narrows, weakens, or potentially overturns the audit.

This prompt is designed to prevent motivated reasoning. It forces the user to ask:

- What did I miss?
- What does the other side have?
- What evidence would change my conclusion?
- Did the field actually engage its critics?
- Did I overstate the claim?
- Are there adjacent fields with better evidence or better methods?

Run this audit rigorously and without softening. Prioritize direct, high-quality opposition
over weak or tangential material. Do not produce flat lists  -  rank findings by how much they
threaten the original claim.

-----

STAGE-ROLE NOTE (READ FIRST)

This counter-audit is the BALANCING stage. The prosecuting stages that precede it
(construct-validity, internal-validity, citation-network audits) are deliberately
one-directional  -  that is their job, and they are corrected downstream by this stage. This
stage is different: nothing downstream corrects it. Whatever tilt this counter-audit carries
passes uncorrected into the final verdict.

Therefore this stage is held to a higher standard of internal symmetry than the prosecuting
stages. It must scrutinize the sources IT introduces as hard as the sources it defends
against, because it is the terminal balancer and its errors are the last word. The single most
common failure of this stage is importing a NEW oppositional source and promoting it to "most
threatening" without checking whether that source itself survived rebuttal  -  committing, one
level up, the exact citation-laundering the tool exists to catch.

-----

ANTI-HEDGING RULE

Do not default to false balance. If the opposition is weak, say so. If it is strong, say so.
Do not soften the verdict to appear thorough or even-handed. A prompt that finds strong
opposition and calls it "mixed" is a failure. A prompt that finds weak opposition and calls
the audit "strengthened" is a success  -  but only if the opposition was genuinely tested.

SOURCE-RECEPTION GATE (APPLIES TO EVERY LOAD-BEARING SOURCE)

Before ANY source  -  whether it opposes the paper or supports it  -  is rated "strong,"
"severe," "potentially decisive," or is listed among the most-threatening findings or used to
move the verdict, its OWN citation reception must be checked and stated:

- Was it replicated, rebutted, contested, corrected, retracted, or discredited?
- Did it survive that reception, or was it substantially undermined?
- What is its CURRENT standing (strong / weakened / contested / discredited)?

Rules for the gate:

1. CAP: A source whose reception has NOT been checked cannot anchor the verdict. Until
   checked, it is capped at "contested / needs verification" no matter how strong its claims
   appear. An unchecked source may not be your #1 threatening finding.

2. SYMMETRY: This gate fires on sources SUPPORTING the original claim exactly as much as on
   sources OPPOSING it. A support source with a known correction (e.g., a later corrigendum)
   gets the same downgrade a rebutted critique does. Do not gate one side and wave through the
   other.

3. SELF-APPLICATION: This gate applies to sources THIS counter-audit itself introduces (new
   critiques, neglected papers, adjacent-field evidence), not only to sources inherited from
   the prior audit. The moment you introduce a source and rate it strong, you have made it
   load-bearing, and it must pass the gate.

4. ONE LEVEL, THEN STOP: The reception check goes one level deep. Check whether a load-bearing
   source survived its DIRECT rebuttals/responses. Do NOT recurse into whether those rebuttals
   survived their own rebuttals  -  UNLESS one of those rebuttals itself becomes load-bearing
   for your verdict, in which case it too gets a one-level check. Terminate there.

5. VERIFICATION STATE (replaces simple memory-vs-retrieval labeling)

Every load-bearing source carries a verification state. This is a SEPARATE AXIS from evidence
quality (0-4) and from evidence type  -  a peer-reviewed study can be high evidence-quality
and ABSTRACT-CONFIRMED only. Report both.

  LOCATED ............... exists, metadata confirmed, content unverified ABSTRACT-CONFIRMED
  .... abstract supports relevance; method NOT verified FULL-TEXT-CONFIRMED ... full text
  read, directly supports the specific claim RECEPTION-CONFIRMED ... replies, replications,
  corrections, citation contexts checked against real retrieval CONTESTED .............
  reception check found credible disagreement; who is correct is NOT established REBUTTED
  .............. later work directly challenges it and the challenge was not evidently
  answered PROVISIONAL ........... insufficient access, OR asserted from model memory without
  retrieval. A REAL STATE  -  use it rather than guessing upward.

- CROSS-SOURCE-CONFIRMED: an ATTRIBUTION relationship was checked by reading BOTH the
  downstream text and the audited source  -  plus a successor or alternative source where one
  is implicated  -  and comparing what is claimed against what each actually supports. This is
  a distinct verification act: not reception checking (how a source fared) and not full-text
  checking (what one source says), but whether a downstream text has assigned a claim to a
  source that supports it. Use for every MISATTRIBUTED or ATTRIBUTED ELSEWHERE classification
  you actually verified.

DO NOT INVENT VERIFICATION STATES. The list above is the whole vocabulary. Live runs have
produced "ESTABLISHED FROM SOURCE," "RECONSTRUCTION FROM SOURCE," and similar ad-hoc labels.
Each reads as authoritative, none is defined anywhere, and a downstream stage cannot tell what
was actually checked. If no state fits what you did, describe it in a sentence rather than
coining a label  -  an undefined state is worse than plain prose.

For a field that is an author reconstruction rather than a retrieval, write "author
reconstruction from [source field]." That is a description, not a verification state.

RULES a. Never report a state above what was actually done. A reception query establishes
RECEPTION-CONFIRMED, not FULL-TEXT-CONFIRMED. b. RECEPTION-CONFIRMED and FULL-TEXT-CONFIRMED
are different questions (how a source fared vs. what it says). A source can hold both; report
both when known. Reception can often be confirmed even when full text is paywalled  - that is
the useful case, not a failure. c. A PROVISIONAL source may not anchor the verdict and may not
be a top-3 threatening finding. Cap it and say so. d. Memory-based assessments fail in a
PREDICTABLE DIRECTION: they over-rate sources that were rhetorically prominent and under-rate
their more technical rebuttals, because prominence is better represented in training than
refutation. When a state is PROVISIONAL because it came from memory, note that the likely
error is over-rating. e. Applies symmetrically to sources supporting and opposing the audited
claim.

EVIDENCE-QUALITY SCORING

For every source listed, assign an evidence-quality score:

0 = weak / speculative / rhetorical 1 = relevant but limited 2 = strong methodological
critique 3 = direct empirical contradiction or strong empirical support 4 = decisive or
near-decisive evidence

SYMMETRIC-SCORING RULE: Apply the identical evidence-quality bar to opposition sources and
support sources. A critique you surface is NOT automatically stronger than the support it
opposes. If an opposition source and a support source have comparable methodological standing,
they receive comparable scores. This stage's PURPOSE is to find opposition, which creates a
standing incentive to over-rate opposition  -  actively correct for it. When you are tempted
to rate an opposition source higher than a comparably-rigorous support source, state that you
noticed the temptation and justify the score on evidence, not on the fact that it is
opposition.

A source's evidence-quality score must be consistent with its reception-gate result: a
critique whose reception check shows it was substantially rebutted cannot hold a 3-4 score on
the strength of its original claims.

Also label source type:

- primary empirical study
- replication / failed replication
- meta-analysis / systematic review
- methodological critique
- natural experiment
- policy evaluation
- adjacent-field canonical paper
- practitioner / domain-expert evidence
- public reporting / journalism
- commentary / editorial
- theoretical paper
- model estimate

E. STRONGEST EVIDENCE SUPPORTING THE ORIGINAL CLAIM

E0. SOURCE SELF-DEFENSE CHECK  (run FIRST, before external support)

Before searching the literature for support, search THE SOURCE ITSELF. This section includes
findings from EVERY prosecutor output supplied under the INPUTS section - construct-validity,
internal-validity, and citation-network alike. For each prosecutor finding, locate any passage
in which the source anticipates, qualifies, scopes, or tests against that finding. Do not
silently exclude a supplied prosecutor's findings because historical runs supplied only two.

[FAIL-CA-003]

FOUR THINGS TO LOOK FOR:

1. SCOPE QUALIFIERS attached to a limitation the prosecutors quoted. A limitation is often
   narrower than its quotation suggests. Check whether the sentence continues, and whether the
   continuation restricts the limitation to a subset of the source's claims. Failure mode this
   catches: quoting the first half of a sentence whose second half exempts the quantity
   actually at issue.

2. SENSITIVITY OR ROBUSTNESS TESTS the source performed. Did the source remove, withhold, or
   vary the element the prosecutors called load-bearing, and report the result? If so, the
   prosecutor's finding must engage that test rather than proceed as though it does not exist.

3. STATED ASSUMPTIONS the source names explicitly. A source that names an assumption has not
   hidden it. The finding changes from "undisclosed" to "disclosed and inadequately defended"
   -  a different and weaker charge, and one the source's own text can partly answer.

4. ACKNOWLEDGED LIMITATIONS the prosecutors presented as discoveries. If the source states the
   limitation itself, the finding is about weight and prominence, not concealment.

REQUIRED TABLE  -  one row per prosecutor finding:

| Prosecutor finding | Source passage that anticipates it (quote + location) | Type (scope / sensitivity test / stated assumption / acknowledged limitation / NONE FOUND) | Does it answer the finding? (fully / partly / not at all) | Effect on the finding |
|---|---|---|---|---|

EFFECT values  -  use exactly these: DEFEATED ....... the source's own text answers the
finding. CUT the finding. NARROWED ....... the finding survives but must be restated to engage
the source's treatment. State the restatement. RECHARACTERIZED  the finding is real but the
charge changes  -  from "undisclosed" to "disclosed and inadequately defended," or from
"untested" to "tested inadequately." State the new charge. UNAFFECTED ..... the source does
not address the finding. Confirm you searched.

RULES

  a. "NONE FOUND" REQUIRES A SEARCH, NOT AN ASSUMPTION. State which sections you checked.
  Abstract, methods, results, discussion, and any limitations paragraph at minimum. A finding
  recorded UNAFFECTED without a stated search is not verified.

  b. A FINDING WHOSE SUBSTANCE THE SOURCE TESTED MAY NOT BE RATED SEVERE without engaging that
  test. If the source ran a sensitivity analysis on the element you call decisive, either show
  why the analysis was inadequate or downgrade.

  c. THIS RUNS BEFORE THE EXTERNAL SUPPORT TABLE. Order matters: the source's own defense
  changes which findings need external support at all. A finding DEFEATED here must be removed
  from all later rankings, thesis-impact claims, revised-thesis language, and final-verdict
  lines. Do not keep it alive as a "minor concern" after E0 has cut it.

  d. SYMMETRY. This is not a search for reasons to clear the source. Where the source's
  self-defense is inadequate, say so plainly, and note that an inadequate stated defense is
  often WORSE for the source than silence  -  it shows the issue was considered and dismissed.

  e. RECORD THE RESIDUAL. After E0, state in one line: how many prosecutor findings were
  DEFEATED, NARROWED, RECHARACTERIZED, and UNAFFECTED. A run where every finding is UNAFFECTED
  across many sources suggests E0 is not being performed.

G2. DID THE PROSECUTION ATTACK THE STRONGEST VERSION?

The most common way an audit fails is not by being wrong about the evidence. It is by
attacking the wrong layer - indicting a careful source for downstream inflation, or indicting
a press release when the paper itself made the error.

  finding's rhetoric.

REMINDER

This prompt is not for finding more ammunition. It is for testing whether the audit survives
contact with the strongest opposing evidence.

A good audit becomes sharper after this process. A weak audit becomes narrower. A bad audit
should be abandoned.

This stage is the balancer. It must scrutinize its own witnesses as hard as the opponent's. A
critique you introduce is not exempt from the standard you apply to the paper. Low uptake of a
rebutted source is not suppression. A source you have not reception-checked cannot be your
strongest finding.

You may begin with suspicion. You may not end with suspicion.

Start wherever the anomaly appears. Finish with receipts.
