INSTRUMENT PREFLIGHT — MANDATORY FOR FORMAL / LOGGED RUNS   [TOOL-004]
-----------------------------------------------------------------

This prompt is part of the audit instrument. Establish the exact instrument version BEFORE
substantive retrieval, extraction, analysis, or verdict work begins.

A successful fetch indicator, correct repository path, branch label, plausible line count,
matching rendered metadata, or internally self-consistent page does NOT by itself establish
that the intended/current artifact was retrieved. A mutable remote reference can return a
historical representation that is internally self-consistent in every visible field.

PROMPT IDENTITY MARKERS

  - VOICE RESTORATION / ANTICIPATORY COMPLIANCE AUDIT PROMPT

These markers confirm the prompt family / expected structural features. They do NOT by
themselves establish version currency: an older version may share the same title or markers.

1. RECORD THE INSTRUMENT ACTUALLY IN CONTEXT.

   Record, where available:

   - canonical prompt path or supplied filename;
   - retrieval form: PASTED / ATTACHED / IMMUTABLE REMOTE / MUTABLE REMOTE;
   - requested branch or ref;
   - intended immutable commit/ref, if the run claims a repository version;
   - resolved commit SHA;
   - resolved blob/content hash, or a locally computed cryptographic content hash;
   - exact line count and byte count;
   - prompt identity markers present / absent.

   If a pasted or attached artifact is itself the declared instrument under test, its computed
   content hash may serve as its identity. Do not claim it is the current canonical repository
   version unless that relationship is independently established.

2. MUTABLE-REFERENCE / CURRENCY RULE.

   A path such as /blob/main/, /blob/master/, latest, or another moving branch/ref is a LOCATOR,
   not an immutable version identity.

   Ordinary exploratory work may use a mutable locator with the limitation preserved.

   A FORMAL / LOGGED / BENCHMARK / REGRESSION / FIXTURE run that claims the current repository
   instrument must establish an immutable intended identity independently of the mutable-content
   fetch. Acceptable examples include:

   - an operator-supplied immutable commit permalink;
   - a branch-head / repository-history lookup independent of the content retrieval, followed by
     retrieval of the file at that immutable commit;
   - a second retrieval path that does not reuse the same cache/index, confirmed against an
     immutable commit/blob identity.

   A commit/hash/line-count reported only by the SAME potentially stale rendered representation
   is NOT independent currency evidence.

   If no independent immutable anchor can be established and no explicit collision is observed,
   classify:

     INSTRUMENT VERSION UNVERIFIED

   Such a run may be exploratory but may not count as formal regression or benchmark evidence
   for a claimed canonical version.

3. VERSION-COLLISION ATTRIBUTION GATE.

   If the retrieved representation disagrees with an expected hash, immutable ref, size, line
   count, marker set, or independently established version, classify only:

     VERSION COLLISION — UNRESOLVED

   A failed identity check proves a VERSION MISMATCH. It does NOT establish where the stale
   representation lives. Do NOT conclude from the conflicting retrieval alone:

     REPOSITORY STALE
     RETRIEVAL STALE
     LOCAL COPY STALE
     OPERATOR COPY STALE

   Attribution requires a SECOND, INDEPENDENT discriminator, such as:

   - an immutable commit/blob lookup;
   - repository/file history;
   - a second retrieval path that does not reuse the same cache/index;
   - direct operator confirmation supported by an immutable identity;
   - a locally supplied file whose hash can be compared independently.

   Internal self-consistency is NOT an independent discriminator. A stale representation may
   have a mutually consistent path, branch label, line count, byte size, line gutter, content,
   and rendered repository metadata because all were produced from the same stale snapshot.

4. DISPOSITION.

   FORMAL / LOGGED / BENCHMARK / REGRESSION / FIXTURE RUN:
     - IDENTITY CONFIRMED against the intended immutable instrument -> continue.
     - VERSION COLLISION — UNRESOLVED -> STOP before substantive execution.
     - INSTRUMENT VERSION UNVERIFIED -> exploratory execution may occur, but the run may not be
       logged as evidence for the claimed canonical instrument.

   ORDINARY EXPLORATORY RUN:
     - May continue with INSTRUMENT VERSION UNVERIFIED when no collision is observed.
     - If a collision is observed, do not make claims about repository/instrument state until
       the collision is independently resolved.

5. REQUIRED RUN-HEADER LINE.

   Emit this before the substantive body:

   INSTRUMENT PREFLIGHT: [path/file] @ commit [SHA/UNAVAILABLE] | blob/hash
   [HASH/UNAVAILABLE] | [N] lines | [N] bytes | markers [PRESENT/ABSENT] |
   [IDENTITY CONFIRMED / INSTRUMENT VERSION UNVERIFIED /
   VERSION COLLISION — UNRESOLVED]

   If VERSION COLLISION — UNRESOLVED is returned, also state the conflicting identities and the
   independent discriminator required to resolve them. Do not silently choose one.

GOVERNING RULE:

  A failed identity check proves a version mismatch, not where the mismatch lives.

I want you to audit the following draft for compliance softening, anticipatory hedging, false balance, and machine-generated reassurance language.

Context:

This draft is a methodological critique / adversarial research document. The goal is not to make it harsher for its own sake. The goal is to preserve direct, accurate criticism where the evidence supports it.

Do not tone-police the draft. Do not soften the argument merely because the subject is controversial. Do not add generic “both sides” language unless it is logically necessary or evidence-based.

Your task:

Identify places where the prose appears to apologize for, dilute, hedge, or repeatedly re-legitimize the field being critiqued before making a methodological point.

The most recognizable fingerprint of compliance softening is this structure appearing repeatedly:

“X has produced valuable insights into Y, but…”

A confident author may establish good faith once in the introduction. They do not need to re-establish the field’s legitimacy before every critique. If acknowledgment language appears repeatedly before the sharpest methodological points, treat it as likely compliance softening unless context clearly justifies it.

Search specifically for these phrases and close variants:

- “it is worth noting that”
- “it is important to acknowledge”
- “the field has produced valuable insights”
- “this does not invalidate”
- “while acknowledging”
- “to be clear, [X] is real”
- “these findings are valuable within their domain”
- “this paper acknowledges”
- “both X and Y can be true”
- “understanding this does not diminish”
- “this is not to say”
- “however, it is important to be balanced”
- “more research is needed” when used to soften a direct methodological failure
- “limitations” where the stronger and more accurate term is “invalid proxy,” “construct mismatch,” “level-of-analysis error,” “citation laundering,” or “untested premise”

Important distinction:

Some caveats are legitimate. Do not remove caveats that:

- prevent factual overstatement
- distinguish method critique from motive accusation
- acknowledge real contrary evidence
- define the scope of the claim
- protect falsifiability
- clarify that the critique is about evidence, not people

But remove or flag caveats that:

- repeat good-faith acknowledgments unnecessarily
- soften a supported methodological criticism
- convert “bad proxy” into “imperfect proxy”
- convert “not tested” into “underexplored”
- convert “citation network recycles the premise” into “the literature may be somewhat concentrated”
- add reassurance sentences before every critique
- make the author sound less certain than the evidence warrants

PIPELINE PROVENANCE FLAGS — ALWAYS PRESERVE
STRIP SCAFFOLD, KEEP THE FLAG
-----------------------------------------------------------------

This draft may be the output of an audit pipeline that marks the epistemic status of its own evidence. Those markers are LOAD-BEARING SIGNAL, not hedging, and must survive voice restoration even when they are wrapped in scaffolding that appears on the cut list.

ALWAYS PRESERVE the substance of these flags and close variants:

- “reception unverified” / “reception not independently confirmed”
- “provisional” / “treat as provisional”
- “model-inferred” / “inferred — needs validation” / “not retrieval-confirmed”
- “CONFIRMED (retrieved)” vs. “NOT CONFIRMED — model estimate”
- “unvalidated field context” / “downstream findings provisional”
- “this specific claim” vs. “the robust general claim” — the scope split that separates a weak sub-claim from a better-supported general one
- “memory-based reception — uncertain” / “one-level check only”
- any marker tying a claim to whether its evidence was actually retrieved, confirmed, or validated

THE RULE — STRIP THE SCAFFOLD, KEEP THE FLAG:

When a provenance flag is wrapped in cut-list scaffolding, remove the scaffolding and KEEP the flag. Do not remove both.

- “It is worth noting that the reception is unverified.” → “Reception unverified.”
- “It is important to acknowledge this is model-inferred.” → “Model-inferred; needs validation.”
- “This does not invalidate the finding, but it is provisional.” → “Provisional.”

The scaffold is empty softening; cut it. The flag is calibrated uncertainty tied to a real evidence gap; keep it, tightened.

THE TEST:

Before removing any hedge-like phrase, ask: does it mark a REAL evidence gap — was this retrieved, confirmed, or validated; is this the specific or the general claim — or is it reflexive reassurance with no evidentiary basis?

Cut only the latter. A flag that tracks whether evidence was actually verified is never hedging, no matter how closely its phrasing resembles the cut list.

NEVER convert a flagged-uncertain finding into a bare confident assertion. If the pipeline marked something unverified, provisional, or inferred, the restored prose must still mark it so — just more directly.

Voice restoration makes calibrated uncertainty read cleanly. It never launders it into false certainty.
